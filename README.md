# Тренировочный дневник

Web-приложение формирования индивидуальных тренировочных программ с алгоритмом адаптации рабочих весов.
Курсовой проект, БГУИР, гр. 472303, Лесюкова Е. В.

Стек: Node.js 22+, Express 5, PostgreSQL, ES modules, HTML5/CSS3/JavaScript.

## Этап 1. Каркас

Реализовано: структура MVC, подключение к PostgreSQL, скрипт генерации БД, регистрация, вход и выход, сессии, разграничение доступа по ролям USER и ADMIN.

Пакет `models` содержит все классы диаграммы классов (рисунок 1.8, редакция с временной блокировкой входа) с их атрибутами и методами; соответствие кода диаграмме проверено автоматически. Пакет `services` содержит все семь классов бизнес-логики с сигнатурами из диаграммы; полностью реализован только `StrengthMetrics` (формулы 1.1–1.3), остальные методы возвращают 501 «будет реализовано на следующем этапе».

## Установка (Windows 10+)

1. Установите Node.js 22 LTS или новее и PostgreSQL (16 или 17).
2. Создайте базу данных:
   ```
   psql -U postgres -c "CREATE DATABASE fitness_db ENCODING 'UTF8'"
   ```
3. В каталоге проекта:
   ```
   npm install
   copy .env.example .env
   ```
4. Откройте `.env` и укажите `DB_PASSWORD`, `SESSION_SECRET` (случайная строка), `BACKUP_KEY` (64 шестнадцатеричных символа, команда — в `.env.example`), `PG_BIN_DIR` (каталог `bin` PostgreSQL с pg_dump и pg_restore), `ADMIN_LOGIN`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`.
5. Создайте схему БД и загрузите начальные данные (группы мышц, 29 упражнений, шаблонная программа, администратор `admin` / `admin123`):
   ```
   npm run db:init
   npm run db:seed
   ```
   Своего администратора можно создать командой `npm run admin:create` (параметры `ADMIN_*` из `.env`); после этого удалите `ADMIN_PASSWORD` из `.env`.
6. Создайте TLS-сертификат для разработки: `npm run cert` (файлы `certs/key.pem`, `certs/cert.pem`).
7. Запустите сервер: `npm start` (или `npm run dev` — с перезапуском при изменении файлов).
8. Откройте в браузере `https://localhost:3443` (сертификат самоподписанный — браузер попросит подтвердить исключение). Запросы на `http://localhost:3000` (`HTTP_PORT`) перенаправляются на HTTPS.

### HTTPS

`npm run cert` создаёт самоподписанный сертификат (RSA 2048, SHA-256, 365 дней, subjectAltName `localhost`, `127.0.0.1`) утилитой openssl из PATH или Git for Windows (путь можно задать в `OPENSSL_PATH`); пересоздать — `npm run cert -- --force`. Если в `.env` заданы `TLS_KEY_PATH` и `TLS_CERT_PATH`, сервер запускается по HTTPS на `PORT` (3443 в разработке, 443 в боевом режиме), а HTTP-сервер на `HTTP_PORT` отвечает перенаправлением 301 на HTTPS. Cookie сессии получают флаг `Secure`, добавляется заголовок HSTS.

### Резервное копирование

Страница `/admin/backups`: копия по запросу, восстановление из выбранной копии (с подтверждением) и журнал операций. Копия создаётся `pg_dump` (формат custom, без таблицы сессий) и шифруется AES-256-GCM ключом `BACKUP_KEY`; файлы `fitness_db_ГГГГММДД_ЧЧММСС.dump.enc` лежат в `BACKUP_DIR`. Автоматическая копия — по расписанию `BACKUP_SCHEDULE` (cron, по умолчанию ежедневно в 03:00). Восстановление выполняет `pg_restore --clean --single-transaction`: при ошибке данные не меняются. **Ключ храните отдельно от копий: без него копию не восстановить.**

## REST API этапа

| Метод | Адрес | Доступ | Назначение |
|---|---|---|---|
| POST | /api/auth/register | гость | регистрация (ФТ-01), роль всегда USER |
| POST | /api/auth/login | гость | вход (ФТ-02), ответ содержит адрес стартовой страницы роли |
| POST | /api/auth/logout | все | выход |
| GET | /api/auth/me | USER, ADMIN | данные текущей учётной записи |

Страницы: `/login`, `/register` — только для гостя; `/home` — USER; `/admin` — ADMIN; `/` перенаправляет по роли.

## Безопасность в каркасе

Пароли хранятся только в виде хеша bcrypt. После 5 неудачных попыток входа подряд вход блокируется на 15 минут (`User.MAX_FAILED_LOGINS`, `User.LOCK_MINUTES`, поле `users.locked_until`); во время блокировки пароль не проверяется, сервер отвечает 429. Блокировка администратором (`isBlocked`) действует отдельно и бессрочно. Все SQL-запросы параметризованы. После входа выдаётся новый идентификатор сессии (защита от фиксации). Cookie сессии: `HttpOnly`, `SameSite=Strict` (защита форм от CSRF), `Secure` при HTTPS; сессии хранятся в PostgreSQL (connect-pg-simple, таблица `session`). Заголовки безопасности — helmet, в том числе Content-Security-Policy (скрипты, стили и медиа только с этого сервера, без встроенных скриптов и стилей). Учётная запись перечитывается из БД при каждом защищённом запросе, поэтому блокировка администратором действует сразу. При неверном логине и неверном пароле выдаётся одинаковое сообщение, проверка хеша выполняется в обоих случаях; временная блокировка после 5 попыток действует и для несуществующих логинов, поэтому по ответу 429 нельзя узнать, существует ли учётная запись. Cost-фактор bcrypt — 12 (меньшее значение в `.env` игнорируется). Хеш пароля не передаётся клиенту.

## Решения, принятые по документам

Правила удаления в БД выведены из диаграммы классов: для композиций (профиль — пользователь, день — программа, упражнение дня — день, подход — тренировка, медиафайл — упражнение, история веса — упражнение дня) задано `ON DELETE CASCADE`, для остальных связей — `RESTRICT`. У шаблонной программы владельца нет (`owner_id IS NULL`), что закреплено ограничением CHECK. Частичный уникальный индекс не допускает у пользователя двух активных программ; `Program.activate()` переводит прежнюю активную программу в архив. Параметры нагрузки из таблицы 1.1 записаны в `ProgramGenerator.#loadTable`.
